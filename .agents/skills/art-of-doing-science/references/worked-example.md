# 原创案例：从“做一个AI平台”到可验证工程问题

假设一名工程师有两周、已有 Python 基础和 60 条经许可使用的匿名客服问题，想选作品集项目。以下判断只针对这些假设。

三个候选：

- 训练一个通用基础模型：潜在价值大，但现有算力、数据和评估能力缺少合理攻击路径。
- 构建几十种代理组成的平台：有技术吸引力，但没有明确用户痛点，也没有证据表明代理数量是瓶颈。
- 给客服检索结果增加“证据不足”提示及可查看出处：受益者和错误风险具体，已有案例可用于原型与小规模复核。

推荐第三项，理由是能在约束内获得有用证据，不是它在所有情况下更伟大。

## 工作假说

有些错误答案来自检索证据不支持结论。让系统输出引用片段并允许“资料不足”，可能减少无法由资料支持的答案，但也可能增加不必要的拒答。一个替代解释是材料过期；那就需要更新知识源，提示词无法修复它。

## 两周内的第一步

先人工审阅一小批案例确认失败模式，并建立“资料支持/不支持/存在冲突”的判据。把余下案例保留用于尚未看过的问题；本例不指定固定分割比例，因为 60 条材料的类型分布尚未知。

原型只接收问题和授权文档，返回回答、引用和证据不足状态。先在已知案例上检查技术实现，然后在保留案例上比较现有方法与原型：支持性错误、无必要拒答、人工复核用时分别记录。不能只报告“回答看起来更好”。实际调用任何外部服务需要对应任务授权和现有凭据，不因本 Skill 自动获得。

反证：如果新增引用只是复制无关文本，或减少错误的同时把所有问题都拒答，当前方案没有实现目标。若过期资料才是主要问题，应调整为版本与更新检测。

## 从实例到类别

在第二类问题上试验，例如由订单查询换为退款政策。只有证据规则仍成立且结果可复核，才考虑抽取通用接口；不要先搭建插件市场、多代理调度或管理后台。

交付一份可运行演示、匿名评估样例和简短说明：“给谁用、怎样失败、改了哪里、已验证什么、还缺什么”。若没有真人使用，只能声称技术试验完成，不能声称用户价值已验证。

反例：用户只是要求修复一个已定位的 JSON 解析异常，按实际错误修复与验证即可，不能用本 Skill 擅自改选项目或讨论职业方向。
